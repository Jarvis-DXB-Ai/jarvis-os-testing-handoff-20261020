# Execution checkpoints and conservative recovery

Use the existing task coordinator, saved milestones and delivery-evidence/checkpoint records. On interruption identify exact task/agent/issue/run, last acknowledged state, output/dependency hashes, completed parts and uncertain actions. Portable context is the selected task folder, not the whole client archive.

Reconcile native status before continuing. A lost write acknowledgement is not permission to repeat it. Reuse completed independent work only when its inputs are unchanged; affected dependencies need review. Do not switch providers, raise quotas, create extra agents or route to API billing without the task's actual grant.

Allocate the smallest useful team with distinct assignments and declared dependencies. Existing role heads summarise completed work; do not add duplicate strategy leads to appear busy. Capacity is the client's configured limit, not the available role count.

A saved checkpoint is evidence, not an automatic resume trigger. Continue through the existing bounded recovery/correction actions only. Report concrete missing capability or capacity; preserved drafts and a blocked task are preferable to invented completed work.

Use only this assigned task and its actual capabilities. This original Jarvis method adapts reviewed concepts; it does not import third-party execution scripts. See [source review](references/source-review.md) for provenance and rejected instructions.
