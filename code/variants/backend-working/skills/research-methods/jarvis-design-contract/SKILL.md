# Client design contract and rendered review

Start with the client's pinned approved foundation: logo/source roles, colour/type tokens, components, tone and approval revision. If no approval exists, state the proposed values and unresolved decision. Extracted website styles are observations, not automatic brand policy. Preserve the existing project and approved visual direction.

Make composition serve the subject: real product/UI evidence, meaningful scenes, clear reading order and purposeful motion. Retain fixed typography/palette when the brand requires them. Marketing-page inspiration does not justify redesigning the Office dashboard. Never simulate a randomisation script or a browser result.

For a design-system task specify token names/values/source/status, component variants/states, responsive rules and accessible focus/loading/error behaviour. A component must cover its useful states, not just a polished default.

For actual implementation, compare rendered widths, keyboard behaviour and reduced motion using available tools. Distinguish code inspection from rendered observations. Report source/artifact revision and concrete fixes; screenshots establish appearance, interaction outcomes establish behaviour. Reference art is inspiration with attribution, not client-owned artwork. Supply editable output and honest production limits.

Use only this assigned task and its actual capabilities. This original Jarvis method adapts reviewed concepts; it does not import third-party execution scripts. See [source review](references/source-review.md) for provenance and rejected instructions.
