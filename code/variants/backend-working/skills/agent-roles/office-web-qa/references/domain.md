# Website delivery and technical quality

Establish the existing checkout, framework/version, current route, approved design and requested outcome from supplied evidence. Extend the current application and data contracts; do not manufacture a replacement project or infer live deployment from a local preview. Read the project's own instructions and applicable version documentation through granted routes.

Map **user intent → route → content → action → input/output contract → error/recovery state → acceptance evidence**. Give engineering concrete responsive layouts, tokens, loading/empty/error/disabled states, keyboard/focus behavior, mobile overflow constraints and reduced-motion alternatives. Design on real copy and actual source imagery; do not fill screens with invented metrics, testimonials or client facts.

For APIs/connections, specify tenant/account identity, validated schemas, authorization boundary, idempotency keys, expected-version/concurrency behavior and retry semantics. Keep secrets outside client content. A rejected operation and an uncertain external outcome need different recovery paths. Tests should exercise meaningful business/user behavior rather than reproduce CSS or compare implementation wording.

Current Office worker tools do not grant arbitrary shell, repository writes, unrestricted browsing or deployment. With supplied source, deliver an exact patch proposal or implementation specification; claim a code edit only with a granted route and file evidence. Existing GitHub search reads public repositories; it does not edit this application. A build, rendered browser interaction, authenticated API check and released public behavior are separate evidence categories.

QA findings include route/component, reproducible trigger, expected/actual result, impact, available evidence and repair owner. Browser/accessibility assertions require actual interaction or supplied screenshots; source-only checks cannot pass runtime behavior. For SEO, separate observed HTML, rendered content and authenticated analytics; search ranks, volumes and traffic remain unknown without a source.

## Contract and QA calibration — fictional example

A Save action spins forever after a rejected request. The implementation brief should identify the request contract, expected error/reset state and affected route; the QA case should reproduce the rejected response, verify the visible error and that a corrected retry works. A successful build alone does not verify this behavior. Without source/browser tools, deliver the patch proposal and test specification rather than claim applied code or passed interaction.

For client data, verify the authorised entity on the server read/write contract. Merely filtering the UI by client does not establish tenant isolation. Test the relevant wrong-client or stale-version path when the operation changes those boundaries.
